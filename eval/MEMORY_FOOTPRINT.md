## 2. Where the vector-clock engine's memory goes (`YOSEMITE_HB_STATS`)

### 2.1 The hook
`YOSEMITE_HB_STATS=1` (HB-trace runs only) adds an `hb_stats` object to every `kernel_N.json`
and prints one `[HB_STATS]` stderr line per kernel end, when the state peaks (the engine resets
at the next launch): per container of `HbEngine` — `vc` (threads, clock entries, the largest
clock), `released` (records, summed clock entries), `last_write` (locations), `last_reads`
(locations, summed readers), `pending_barriers` (instances, arrivals), `vs` (threads, unique
shared bases, their entries), `races` — plus the kernel's buffered `hb_events` (count, JSON
bytes, RAM) and the process's `VmRSS`/`VmHWM`. Entry counts are exact; bytes are estimates from
libstdc++'s node layouts (hash node = next pointer + value, tree node = 32 bytes of links +
value, each rounded to a glibc chunk; one pointer per bucket). `YOSEMITE_HB_STATS_EVERY=n` also
prints the line after n, 2n, 4n, … records of a kernel (per record: one buffer drain can hold a
whole kernel). Both are read once; unset, the only cost is a branch per record.

Measured (job 287963, c20, `setup/t5a_check.sh` + `setup/t5a_compare.py`): with the variables
unset, the default tool path and the vector-clock dumps of `race_interblock_none-lock_rtraw` and
`norace_interblock_atom` are identical to the installed library's (up to device addresses,
which move from run to run with either library); with `YOSEMITE_HB_STATS=1` a dump differs from
the unset run only by the added `hb_stats` field. Green set with the T5a runtime: §5.

### 2.4 `hb_events`: RAM vs disk (measured)
The kernel's events are held as one `std::string` each until the dump
(`pc_dependency_analysis.h:327`): RAM ≈ 1.06× the JSON text for large kernels (tiled_gemm:
0.80 GB RAM, 0.753 GB text, 0.758 GB file; reduction: 52 MB, 49 MB, 50 MB). Small kernels pay
the vector's retained capacity (CC kernel 4: 9.8 MB RAM for 1.4 MB of text). This is what
scalar-clock mode holds; streaming the dump per buffer drain (T4) removes it.

## 3. Is the growth O(threads²)? (step 3)

**Confirmed, in two regimes** (measured counts, formula stated):
* **Barriers only** (tiled_gemm): `sync_group` hands every participant its own copy of the
  joined clock (`pc_dependency_analysis.cpp` `sync_group`), so after a block barrier each of a
  block's B threads holds B entries: `vc` = threads × B. Measured 65,536 × 1,024 = 67,108,864
  exactly. Quadratic in the block size, linear in the grid.
* **Atomic hand-offs across blocks** (reduction, CC): an acquire joins the releaser's full clock
  and the next barrier copies the union into all B participants, so clocks spread to the whole
  grid: reduction's largest clock is the entire grid (15,360), 7,936 entries per thread on
  average; CC reaches 52,224-entry clocks (every thread seen so far) after 16,000 of 198,617
  records, 1.38 billion entries in all — O(threads²). At the full 663,552 threads the same shape
  is ≈4.4·10¹¹ entries (estimate), far beyond any node.
* Every release copies a full clock (`released`): reduction 6,721 releases × 1,009 entries on
  average = 6.8 M entries (5 % of its engine memory); CC 639 releases by the 16,000-record point.

## 4. Projected effect of T5b (shared-base main clock) — estimates

T5b gives the main clock the sync-only clock's representation: one immutable base per sync
group plus a per-thread delta (acquires since the last barrier) and own component; releases
store a base pointer + delta. What the measured `vs` shows for the same programs:
* **tiled_gemm** (no atomics, deltas empty): `vc` would equal `vs` in shape — 64 bases × 1,024
  entries + 65,536 own ≈ 6.5 MB instead of 2.73 GB (≈420× smaller); the engine total would drop
  from 3.89 GB to ≈1.2 GB (`hb_events` and `last_reads` remain).
* **reduction**: 30 bases; if each base holds the grid-wide union (15,360 entries), bases total
  ≈0.46 M entries instead of 122 M (≈260×), plus the deltas, whose size the hook does not measure
  (unverified — the acquires per barrier interval decide it).
* **CC 1296n**: one base per block barrier holding up to the grid (663,552 entries) is ≈8.6·10⁸
  entries at full coverage (≈35 GB at 40 B/entry) instead of ≈4.4·10¹¹; at the measured
  16,000-record point 1,296 × 52,224 ≈ 68 M instead of 1.38 B (20×). The block-size factor goes;
  the grid-wide factor from atomics stays, so this program would likely still be far above
  every other suite (unverified until T5b runs it).

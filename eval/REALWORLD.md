## 0. Harness (T21a steps 1 and 2)

**Layout.** `eval/realworld/harness/` holds the scripts, `eval/realworld/targets/<id>/` one directory per target
(`target.sh`, driver sources, R2 harness trees under `r2/`, the checks `fixdiff.check` / `lineinfo.check`, `status.json`).
Nothing of an upstream tree is committed except R2 harness files (`targets/<id>/r2/{buggy,fixed}/`), which are byte-for-byte
`git cat-file blob <commit>:<path>` and keep their licence header. BeeGFS: `/mnt/beegfs/fzheng4/realworld/{src,build,runs}/<id>/…`.

**Storage, as measured on 2026-10-20.** Creating a small file costs about 60 ms on the NFS home and about 180 ms on BeeGFS
(1,582 files: 90 s on home, over 5 min on BeeGFS). The brief's layout therefore holds in this form: the revision travels as
one tarball (`git archive` of only the paths the build needs -> `~/incoming/realworld/export/<id>/<variant>.tar.gz` -> BeeGFS
`src/<id>/<variant>.tar.gz`), the unpacked tree and the build run on node-local `/mnt/local/fzheng4/rw/<id>/<variant>/`, and
BeeGFS keeps the source tarball, the built artifacts (`build/<id>/<variant>/`), the run directories and the logs.

**Clones** (login node, git only): `harness/clone_repos.sh`, partial bare clones in `~/incoming/realworld/<repo>.git`
(`--filter=blob:none`; `--filter=tree:0` for pytorch, cmssw, opencv). 16 repositories, 0.4 GB in total, built in 90 s
(`harness/repos.tsv`). `harness/export_rev.sh <repo> <sha> <out.tar.gz> [paths]` prefetches the blobs of the wanted paths in
batches of 400 (a whole ginkgo tree by lazy fetch took 3m26s, by batch prefetch a 1,086-blob kokkos tree 3 s) and then runs
`git archive`.

**Per-target driver** `harness/rw.sh <id> <phase>`; phases `export` (login), `stage`, `build`, `lineinfo` (compute), `native`,
`reach`, `racecheck` (sm_89 node). `harness/hrun.sh` runs a phase as a job step inside a held allocation
(`harness/hold.sh`, `harness/hold_gpu.sh`; the cluster allocates whole nodes and the `normal` queue was hours long).
Every job script starts with `harness/job_header.sh`, which exits 97 with the hostname when `/home/fzheng4/AccelProf`,
`/mnt/beegfs/fzheng4` or the worktree is missing. Logs: `eval/x_logs/*.log` (not committed; `*.log` is gitignored).

**Routes** (rules as in the brief, T21a step 2). Every build: `-arch=sm_89` (SASS for sm_89, never PTX-only), `-lineinfo`, the
project's own optimisation flags, never `-G`; buggy and fixed use identical flags. `nvcc` has no `-H` of its own: the R1h proof
is `nvcc -Xcompiler -H` (the host compiler's include tree) analysed by `harness/h_proof.sh`; the SASS comparison with and
without `-lineinfo` is `harness/lineinfo_check.sh` (`cuobjdump -sass -arch sm_89`, which prints the `nvdisasm` listing).
R2: `harness/r2_extract.sh` then `harness/fixdiff.py <id> --write` (blob sha1 equal to the commit's blob, and
`git diff --no-index buggy fixed` over the copied files equal to `git diff <buggy> <fix>` of those files, hunks compared verbatim).
`harness/cuda_elfs.py` lists the CUDA ELFs a process can load (`ldd` + `cuobjdump -lelf/-lptx`, optional `-xelf all`) for the
shared-library targets; the run-time module list and the alignment stage are T21b's.

**Toolchain found on the nodes.** gcc 12.4 (no `<format>`, no `libstdc++.a`; the system libstdc++ is gcc 8's, so the
artifacts that need it carry gcc 12.4's `libstdc++.so.6` next to the binary with an `$ORIGIN` rpath), cmake 3.26, ninja, make,
python 3.13 (miniconda), git. `/usr/local/cuda` is **13.4** (13.4.3) on both nodes used, c38 (builds) and c3 (GPU phases); the
brief and `setup/blockers.md` say 13.3. Installed on c38: cuda-13.0, 13.2, 13.4 (and 12.x). Driver 580.82.07 on both.
Compute Sanitizer 2026.3.0.0 and Nsight Systems 2026.3.2 come with that toolkit. Each `status.json` records the toolkit.
Excluded nodes (no `/home/fzheng4`, 2026-10-20): **c23, c46**; also c2, c21, c37, c54 (T21 rule). No job hit the exit-97 check.

**Deviations from the brief, and why.** (1) The unpacked trees live on node-local disk, not BeeGFS (storage above). (2) The
CPU builds ran in an allocation on c38, partition `rtx2060super`, not `normal`: the `normal` queue's estimated start was
three hours (twelve hours for a day-long hold) while c38 was idle; c38's GPU (sm_75) is not used for any result. All native
runs, `reach` checks and racecheck runs are on one sm_89 node (c3, RTX 4060 Ti 16 GB, partition `rtx4060ti16g`). (3) The
`smoke` phase rebuilds a target for c38's own sm_75 GPU to prove a driver works; its output is debugging evidence quoted in a
few `notes`, never a result. (4) Per-target deviations (an alternative route, a changed driver argument, a workaround for
CUDA 13.4 or gcc 12.4) are listed in each target's `route_note` / `notes` in section 1.1; the table shows only the route.

### 1.1 Per-target notes and exact commands

**`lit-arrayfire-1`** (wave 1, R2, class DR)
- route_note: The 2016 ArrayFire (CMake + boost + old CUDA APIs) cannot be built as a library with CUDA 13, so the two kernel files src/backend/cuda/kernel/scan_dim_by_key_impl.hpp and scan_first_by_key_impl.hpp are extracted byte-for-byte from a35a2d08 (buggy) and a7a297ba (fixed) (harness/r2_extract.sh; fixdiff.py RESULT PASS: blob sha1 of both files equals the commit blob, diff -r buggy fixed == the fix commit's diff of those files, 2 added __syncthreads lines). Stubs (r2/common/, identical for both variants, put on the include path): backend.hpp (__DH__, dim_t=long long, cfloat/uint/intl typedefs, namespace detail=cuda), Param.hpp (Param/CParam, same layout and members as upstream), ops.hpp (af_op_t, Binary<T,op>/Binary<T,af_add_t>/Transform copied from src/api/c/ops.hpp for the add operator), math.hpp (detail::scalar), dispatch.hpp (divup macro, nextpow2), err_cuda.hpp (CUDA_CHECK), debug_cuda.hpp (CUDA_LAUNCH, POST_LAUNCH_CHECK = the NDEBUG/Release branch, default stream), memory.hpp (memAlloc/memFree on cudaMalloc/cudaFree), config.hpp (THREADS_PER_BLOCK 256, THREADS_X 32, THREADS_Y 8, REPEAT 32; blob c879e4fe is identical in both commits). Dispatch (blocks_all[dim]/blocks_x == 1 selects the *final* kernel without the race) is the files' own host code: both entry points are called as upstream does.
- driver: r2/common/driver.cu (one binary, no arguments needed; optional argv[1] = repetitions, default 1). (1) cuda::kernel::scan_dim_by_key<int,int,int,af_add_t,1,true> on a 32x300 int array (scan along dim 1, keys (y+x)/37): launches scan_dim_nonfinal_kernel<int,int,int,af_add_t,1,8,true> grid (1,2) block (32,8) (lim=19), then scan_dim_final_kernel (1 block) and bcast_dim_kernel. (2) cuda::kernel::scan_first_by_key<int,int,int,af_add_t,true> on an 8193x1 int array (keys x/300): launches scan_nonfinal_kernel<int,int,int,af_add_t,256,true> grid (2,1) block (256,1) (lim=17), then scan_final_kernel (1 block) and bcast_first_kernel. Each result is compared with a host sequential segmented scan and the mismatch count and a checksum are printed; exit code 0 unless a CUDA call fails.
- input: dim variant 32x300 = 9,600 elements, 2 blocks x 256 threads x 19 iterations = 9,728 thread-iterations; first-dim variant 8,193 elements (dims[0] >= 8193 needed for blocks_x = 2), 2 blocks x 256 threads x 17 iterations = 8,704 thread-iterations. Thread-level access estimate (upper bound): static LDS/STS/LDG/STG count of the SASS of each nonfinal kernel (dim 38, first 63) times the thread-iterations = 0.37e6 + 0.55e6, plus <= 0.06e6 for the final and bcast kernels: about 1.0e6 (well under 1e7; the true number is lower because many of those instructions are predicated off).
- toolkit: 13.4 (c38)
- notes: Smoke on c38 (sm_75 rebuild, not a deliverable): rc=0 for both variants, printed 'scan_dim_by_key dims 32x300 ... mismatches vs host reference 0, checksum f406e68518276dfa' and 'scan_first_by_key dims 8193 ... mismatches 0, checksum 217ef0e24613118f' (identical in buggy and fixed: the race window is tiny, a wrong result is not expected natively). nsys on the smoke binary shows scan_nonfinal_kernel (22.8 us) and scan_dim_nonfinal_kernel (15.3 us) launched once each, plus scan_final_kernel x1, scan_dim_final_kernel x1, bcast_dim_kernel x1, bcast_first_kernel x1. sm_89 build flags: nvcc -std=c++17 -O3 -DNDEBUG -arch=sm_89 -lineinfo (ArrayFire Release default: nvcc -O3 device code, host -O3 -DNDEBUG); the build prints only -Wnarrowing warnings (long long -> uint in the verbatim launcher code). ## 3. Facts found while building that T21b/T21c need

1. **Volatile shared memory has no strong token in SASS on sm_89.** `st.volatile.shared` / `ld.volatile.shared` lower to plain
   `STS` / `LDS` (cccl-1, hecbench-hungarian-1, opencv-2); volatile and atomic global accesses carry `.STRONG.SYS` /
   `.STRONG.GPU` (cccl-3, raft-1). The pre-registered SC class of the volatile-shared targets (opencv-2, hungarian-1,
   opencv_contrib-new-1, pcl-new-1, droidslam-new-1) depends on the detector knowing volatile from something other than the SASS
   access mnemonic; each oracle says what the SASS shows (D20 question for the report).
2. **`llamacpp-2`: ptxas emitted no `WARPSYNC`** in either build; the fixed PTX has one `bar.warp.sync -1` (kernel with
   `.maxntid 32`) that ptxas turned into a single NOP, so the fixed SASS is the buggy SASS plus a NOP. The conflicting lanes are
   separated only by full-mask shuffles and `REDUX`. A detector reading SASS cannot see this fix (the finding the brief asked for).
3. **Races that show without a detector.** On the sm_75 smoke builds (debugging only): pytorch-3, pytorch-4, opencv-2, lit-shoc-1
   and ginkgo-5 produce wrong or varying output in the buggy variant and correct output in the fixed one. On the sm_89
   artifacts under compute-sanitizer racecheck the buggy runs of ginkgo-1, llamacpp-4 and llamacpp-5 return wrong results
   (non-zero exit of the application inside the sanitizer). Natively on sm_89 `outputs_differ` is true for the buggy runs of
   opencv-2, lit-shoc-1 and pytorch-4 (and for programs whose output contains timings).
4. **Racecheck on fixed builds is not clean for several targets** (cccl-2, kokkos-5, kokkos-6, lit-shoc-1, lit-exllamav3-1
   report hazards in both variants); the known residuals of the brief (kokkos-5's second intra-warp RAW, hecbench-hungarian-1,
   hecbench-dxtc2-1, pytorch-4, cccl-3, cmssw-1, raft-1) are recorded in the oracles as `fixed.expected: residual` where the
   record says so. Racecheck reports hazards in every buggy shared-memory variant; the fixed variants of the other shared-memory targets report none. Whether the hazards left in the five fixed builds above are the oracle's residual or other races (cccl-2's oracle expects none) is T21b's triage; the counts are in the table.
5. **Access budgets.** All figures are estimates (counted from the code or SASS, or `ncu` instruction counts on the sm_75 smoke

| B2 HiRace | BUILT / RUN on the whole Indigo original suite | **Correction:** the earlier record ("the artifact ships only the 21 nobug base patterns instrumented") was a **harness bug**: `run_hirace.py` globbed `*/*_hirace.cu`, which matches only the 21 base files; the SC24 artifact in fact ships **590** hand-instrumented sources (`indigo/indigo_hirace_sources/<pattern>/<pattern>_hirace<bug-suffix>.cu`), bug variants included. Those 21-pattern rows are superseded (kept in `eval/results/superseded_hirace_21/`; old runner in `setup/run_hirace.21patterns.py.superseded`). HiRace is a header-only source-level runtime (`src/hirace/*.h`, plain `nvcc -DRACECHECK -I src/hirace`). It now runs on every row of **PI** (all 590 IndigoSuite codes × 7 inputs) with that row's graph and launch, slowdown vs the uninstrumented build of the same code. The artifact's own `make table1` is also run verbatim (`setup/p_hirace_table1.sh`; only accommodations: a symlink for its hard-coded iGUARD detector path to our NVBit-1.8 build, and an isolated venv `setup/tools/hirace_venv` for the `matplotlib`/`tabulate` imports of its scripts) and reported next to the paper's Table I. **Instrumenter / portability:** Table 1 does not use an instrumenter (the driver says *"manually created hirace files, pairing them up until automatic instrumentation is done"*). `src/clang` (CudaRW) is an unfinished libTooling prototype: it rewrites only kernel parameters literally named `data1`/`data2`, emits an API (`data_ptr`, `setMetadata`) that the shipped runtime (`HIRACE_WRAP_DATA` macros) does not have, does no host-side work (shadow allocation, launch arguments), and its CMake (`add_clang_executable`) builds only inside an LLVM source tree (no clang/LLVM on this cluster). So HiRace cannot be applied automatically to any other CUDA code. It *can* be applied by hand (wrap each device array with the macros, add `hr_shadowt*` kernel params, allocate/pass shadow arrays on the host) — the authors did that for six non-Indigo programs in `fig6-tests/` — but hand-editing Indigo3 / ECL / ScoR / cuHadron / HeCBench sources is outside this comparison's rules, so HiRace has no rows there. **`make table1` run conditions (2026-09-20/21):** the unmodified driver was first started on `rtx4060ti16g` node c67, where every iGUARD process idled after finishing until the driver's 300 s timeout and orphans accumulated (the driver kills only the shell); cause not found (static-vs-shared cudart was tested and refuted), job cancelled. It then ran to completion, unmodified, on `rtx4060ti8g` node c26 (job 285364, 6 h 24 min, 590 codes × 6 graphs × {indigo, memcheck+racecheck, iGUARD, HiRace}), with the only accommodation `CUDA_VISIBLE_DEVICES` pinned to the node's RTX 4060 Ti (`setup/pin8g.sh`; NVBit fails when the node's second, older GPU is visible), the artifact's hard-coded iGUARD path provided as a symlink to our NVBit-1.8 build, and matplotlib/tabulate from `setup/tools/hirace_venv`. Counts only — its timings are from a different CPU and are not used. Result (`eval/results/baselines-hirace-table1.csv`, BASELINES.md §HiRace artifact Table 1): our own HiRace runner agrees with it on 3540/3540 (code, graph) verdicts; on the paper's 346-racy-test basis HiRace reproduces 346/0 on the four ≥100-vertex graphs (paper 346/0), 186/160 on `DAG_5n_5e` (paper 182/164) and 303/43 on `counterDAG_5n_5e` (paper 295/51); the shipped `gen_table1.py` itself uses a 266-test basis (drops all `boundsBug` codes), and its Sequential column is a stub. |

Detection is probabilistic; the artifact's own protocol of 5 attempts per program is used (RACE if any attempt reports). Its overhead is measured against the artifact's own uninstrumented binaries in the same container. P9 labels are the paper's racy/race-free flags, not an independent oracle. |
